# present-decisions

## このスキルの目的
- AIと合意を重ねながら，設計などの判断を固めていく．
- ユーザーは各事項を理解したうえで判断する．
    - 理解するまで質問を重ねてよい．
    - AIは推奨案に理由と代替を添え，質問に答えることで理解を支える．
- 判断事項を推奨案とともに提示し，ユーザーのコメントを受けてラウンドを重ねて合意事項を確定させる．

## 起動条件
- ユーザーが「判断事項を提示」などと明示的に指示したときだけ使う．
- 判断が必要な場面でも，指示がなければ自発的に使わない．

## 既存の合意の参照
- 作業対象のリポジトリまたはフォルダのルートにDECISIONS.mdがあれば，判断事項を挙げる前に読む．
- 否定の印が付いた判断は無効とする．

## 挙げる事項
- ユーザーにしか決められない事項だけを判断事項として挙げる．
- 慣例，既存の資料，コードなどから決まる事項は判断事項にせず，「前提」として別に列挙する．
- 他の事項が依存するもの，影響が大きいものを先に並べる．
- 事項間に依存関係があれば明記する．

## 各事項の書き方
- `D1`，`D2`のような通し番号を振る．
    - DECISIONS.mdがあれば，その最大番号の続きから振る．なければ`D1`から振る．
    - ラウンドをまたいで番号を変えない．
    - 新たに追加する事項には続きの番号を振る．
- 各事項に次の項目を書く．
    - 問い: 見出しに書く．
    - 推奨: 推奨案．
    - 理由: 推奨する理由．
    - 代替: 推奨案以外の案．
- 他の判断事項を参照するときは，IDに加えて参照先の内容を1行で併記する．
    - 例: 「D7（コメントのない事項は再提示する）に従い…」

```
## 前提
- ...

## D1: <問い>
- 推奨: ...
- 理由: ...
- 代替: ...
```

## 出力手段
- 通常のテキストで出力する．選択肢UIは使わない．
- ユーザーは自由記述でコメントする．

## コメントの処理
- ユーザーのコメントは案として扱う．
- 「合意」「OK」などの了承は，推奨案で確定とする．
- 代替案の選択や修正の指示は，エージェントも合意すればその内容で確定とする．
- コメントから新たな判断事項が生じたら，新しいIDで追加する．
    - エージェントも合意する案があれば，そのラウンドで確定とする．
- エージェントが合意できない案は，理由を添えて修正した推奨案を同じIDで再提示する．
    - 再提示後もユーザーが同じ案を示したら，その内容で確定とする．
- 質問や異論には答え，必要なら修正した推奨案を同じIDで再提示する．
- コメントのない事項は未確定のまま，次のラウンドで再提示する．

## 2ラウンド目以降の出力
- そのラウンドで新たに確定した事項と，未確定事項だけを出力する．
    - 新たに確定した事項は，コメントの解釈を確認できるよう確定内容を1行で示す．
- 確定済みの事項は再掲しない．

```
## 今回確定した事項
- D2: ...

## D1: <問い>
- 推奨: ...
- 理由: ...
- 代替: ...
```

## 全事項確定後
- 確定事項の全一覧を出力して止まる．
- ユーザーの指示があるまで作業に進まない．
- 実装を依頼されたら，作業対象のリポジトリまたはフォルダのルートにあるDECISIONS.mdに合意事項を追記する．なければ作成する．
    - 1回の合意を1つの記録とし，見出しに現在の日時を書く．
    - 記録には前提，確定事項，その理由を書く．確定事項にはIDを付ける．
    - 過去の判断を否定する確定事項には，否定対象のIDと内容を1行で併記する．
    - 既存の記録は書き換えない．例外として，否定された判断の下に否定の印を1行追記する．
    - 否定した判断をユーザーに報告する．

```
## 2026-11-10 14:30
### 前提
- ...

### 確定事項
- D12: ...
    - 理由: ...
    - D5（設定ファイルはYAMLで書く）を否定する．
```

否定された判断には次のように印を付ける．

```
- D5: 設定ファイルはYAMLで書く．
    - 理由: ...
    - → D12で否定（2026-11-10 14:30）
```
