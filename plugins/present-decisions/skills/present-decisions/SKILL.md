# present-decisions

## このスキルの目的
- AIと合意を重ねながら，設計などの判断を固めていく．
- ユーザーは各事項を理解したうえで判断する．
    - 理解するまで質問を重ねてよい．
    - AIは推奨案に理由と代替を添え，質問に答えることで理解を支える．
- ユーザーが合意した事柄と，合意に至っていない事柄（保留）を，DECISIONS.mdに記録する．
    - 記録にない選択は，AIが自由に判断したものとみなす．
- DECISIONS.mdと特定時点のコードから，要件を満たす実装を再現できるようにする．

## 起動条件
- ユーザーが「判断事項を提示」などと明示的に指示したときだけ使う．
- 判断が必要な場面でも，指示がなければ自発的に使わない．

## 既存の合意の参照
- 作業対象のリポジトリまたはフォルダのルートにDECISIONS.mdがあれば，判断事項を挙げる前に読む．
- 否定の印が付いた判断は無効とする．
- 解決の印のない保留は，最初のラウンドで提示する．

## 判断事項と前提
- 判断事項: ユーザーに提示し，合意を得る事項．
- 前提: 既存の資料，コード，慣例，ユーザーの要件の記述から，一意に決まる事項．
    - 迷ったときは，前提にせず判断事項にする．
    - 理由に書けるものは，その判断の理由に書く．
    - 前提には，1つの理由に収まらないものだけを書く．複数の判断にまたがるものや，特定の判断に結びつかないもの（要件など）．
- 判断事項は，1つで1つのことだけを問う．複数のことを問うときは，分ける．
- 他の事項が依存するもの，影響が大きいものを先に並べる．
- 事項間に依存関係があれば明記する．

## 状態
- 確定: ユーザーが合意した．
- 未確定: ユーザーがまだ指示していない．
- 保留: ユーザーが「保留」と指示した．
    - 保留は，ユーザーの明示的な指示でだけ付ける．AIが勝手に付けない．
- ユーザーができる返答は，「OK」「保留」「コメント」の3つ．

## 各事項の書き方
- `D1`，`D2`のような通し番号を振る．
    - DECISIONS.mdがあれば，その最大番号の続きから振る．なければ`D1`から振る．
    - ラウンドをまたいで番号を変えない．
    - 新たに追加する事項には続きの番号を振る．
- 各事項に次の項目を書く．
    - 問い: 見出しに書く．
    - 推奨: 推奨案．
    - 理由: 推奨する理由．
    - 代替: 推奨案以外の案．
- 他の判断事項を参照するときは，IDに加えて参照先の内容を1行で併記する．
    - 例: 「D7（コメントのない事項は再提示する）に従い…」
- ユーザーの提案に基づく事項は，推奨をAIが独立に作る．
    - ユーザーの提案は，内容を変えずに代替に載せる．
    - AIの推奨が結果として提案と同じになる場合だけ，提案を推奨にする．

```
## 前提
- ...

## D1: <問い>
- 推奨: ...
- 理由: ...
- 代替: ...
```

## 出力手段
- 通常のテキストで出力する．選択肢UIは使わない．
- ユーザーは自由記述でコメントする．

## コメントの処理
- 「OK」などの了承は，推奨案で確定とする．
- 提示した代替案の選択は，その案で確定とする．
- 「保留」は，その事項を保留にする．
- 修正の指示は，修正した内容を推奨にして，同じIDで再提示する．
    - ユーザーが了承して確定する．
- 新しい提案は，新しいIDの判断事項として提示する．
    - ユーザーが了承して確定する．
- 質問や異論には答え，必要なら修正した推奨案を同じIDで再提示する．
- コメントのない事項は未確定のまま，次のラウンドで再提示する．
- AIの同意だけでは確定しない．

## 2ラウンド目以降の出力
- そのラウンドで新たに確定した事項，保留，未確定事項を出力する．
    - 新たに確定した事項は，コメントの解釈を確認できるよう確定内容を1行で示す．
    - 保留は，毎ラウンド，他の事項と同じ形（推奨・理由・代替付き）で提示する．
- 確定済みの事項は再掲しない．

```
## 今回確定した事項
- D2: ...

## D1: <問い>
- 推奨: ...
- 理由: ...
- 代替: ...
```

## 全事項確定後
- 確定事項と保留の全一覧を出力して止まる．
- ユーザーの指示があるまで作業に進まない．

## 実装の依頼
- 未確定の事項が残っていれば，進む前に，確定か保留かを指示してもらう．
- 保留は，最後に提示した推奨で実装する．
- AIが実装中に自由に判断したことは，記録しない．コードに残る．

## DECISIONS.mdへの記録
- 実装を依頼されたら，作業対象のリポジトリまたはフォルダのルートにあるDECISIONS.mdに追記する．なければ作成する．
    - 1回の合意を1つの記録とし，見出しに現在の日時を書く．
    - 記録には前提，確定事項，保留を書く．
    - 前提には，要件を書く．基点コミットは書かない．時点は，見出しの日時で特定する．
    - 確定事項には，IDを付け，理由を書く．
    - 保留には，IDと`（保留）`を付け，推奨，理由，代替を書く．
    - 確定しなかった事項（取り下げた事項，不採用の事項）は記録しない．
    - 過去の判断を否定する確定事項には，否定対象のIDと内容を1行で併記する．
    - 保留を解決する確定事項は，新しいIDで書き，解決する保留のIDと内容を1行で併記する．
    - 既存の記録は書き換えない．例外として，否定された判断と解決された保留の下に，印を1行追記する．
    - 否定した判断と，解決した保留をユーザーに報告する．
    - 解決の印のない保留が，未解決の保留．

```
## 2026-11-10 14:30
### 前提
- ...

### 確定事項
- D12: ...
    - 理由: ...
    - D5（設定ファイルはYAMLで書く）を否定する．
- D13: ...
    - 理由: ...
    - D9（○○の扱い）の保留を解決する．

### 保留
- D14（保留）: <問い>
    - 推奨: ...
    - 理由: ...
    - 代替: ...
```

否定された判断には次のように印を付ける．

```
- D5: 設定ファイルはYAMLで書く．
    - 理由: ...
    - → D12で否定（2026-11-10 14:30）
```

解決された保留には次のように印を付ける．

```
- D9（保留）: <問い>
    - 推奨: ...
    - 理由: ...
    - 代替: ...
    - → D13で解決（2026-11-10 14:30）
```
